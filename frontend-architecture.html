۱ · نمای کلی

یک اپلیکیشن Next.js تک‌سمت‌کلاینت با بک‌اند جدا

فرانت‌اند یک فروشگاه آنلاین قطعات یدکی است که با Next.js 16 (App Router) و React 19 نوشته شده و تقریباً تمام صفحات آن به‌صورت کامپوننت کلاینت ('use client') اجرا می‌شوند. هیچ ارتباط مستقیمی با دیتابیس وجود ندارد؛ همه داده‌ها از یک بک‌اند Express جداگانه (پوشه backend/، پیش‌فرض پورت 4000) از طریق REST و با توکن JWT گرفته می‌شوند.

مرورگر React UI · CSS Modules
←
لایه API src/lib/api.ts · fetch + Bearer
←
بک‌اند Express port 4000 · JWT · zod
←
دیتابیس PostgreSQL · Drizzle ORM

مسیر یک درخواست (در چیدمان راست‌چین از راست به چپ): کامپوننت React تابعی از lib/api.ts را صدا می‌زند؛ این لایه آدرس بک‌اند و توکن را اضافه می‌کند و پاسخ JSON — یا پیام خطای فارسی — را برمی‌گرداند.

چهار لایهٔ مشخص در کد فرانت قابل تشخیص است:

  • لایه مسیر و چیدمان — پوشه src/app بر اساس قواعد App Router: هر page.tsx یک مسیر، هر layout.tsx یک پوسته مشترک.
  • لایه وضعیت سراسری — فقط یک Context وجود دارد: AuthContext برای وضعیت ورود کاربر.
  • لایه ارتباط — src/lib/api.ts (پروکسی HTTP) و src/lib/types.ts (قرارداد TypeScript با شکل داده‌های بک‌اند).
  • لایه UI مشترک — چهار کامپوننت در src/components که بین صفحات بازاستفاده می‌شوند.
فلسفه کلی: حداقل وابستگی خارجی. هیچ کتابخانه state (Redux/Zustand)، هیچ UI-Kit، هیچ axios — فقط React خالص، fetch بومی مرورگر، CSS Modules و TypeScript. تنها «کتابخانه‌های» اضافه، خود Next.js و فونت وزیرمتن از next/font هستند.

۵ · مدل رندر

رندر سرور در برابر کلاینت — تقریباً همه‌چیز کلاینت است

به‌جز دو فایل، تمام صفحات و کامپوننت‌ها با دستور 'use client' شروع می‌شوند؛ یعنی رندر اولیه روی سرور انجام می‌شود اما تعامل و دریافت داده در مرورگر. تنها کامپوننت‌های سروری پروژه:

  • app/layout.tsx — چیدمان ریشه؛ امکان تعریف metadata (عنوان و توضیح سئو) و بارگذاری فونت اینجا فراهم است.
  • app/parts/[id]/page.tsx — یک الگوی «پوسته سرور + محتوای کلاینت»: صفحه سرور params را (که در Next 16 یک Promise است) باز می‌کند و id را به PartDetailClient.tsx می‌دهد.
// app/parts/[id]/page.tsx — کامپوننت سرور
export default async function PartDetailPage({ params }) {
  const { id } = await params;   // در Next.js 16 params یک Promise است
  return <PartDetailClient id={id} />;  // تعاملات → کلاینت
}
نتیجه عملی: داده‌ها بعد از لود صفحه در مرورگر گرفته می‌شوند (نه داخل HTML اولیه)، پس هر صفحه خودش وضعیت «در حال بارگذاری…» و «خطا» را مدیریت می‌کند. این ساده و سازگار با احراز هویت مبتنی بر localStorage است، ولی یعنی از مزایای Server Components برای سئو/سرعت کمترین استفاده شده (بخش ۱۲ را ببینید).
۶ · لایه ارتباط

یک wrapper واحد برای همه درخواست‌ها

فایل src/lib/api.ts تنها دروازه ارتباط با بک‌اند است و چهار کار را به‌صورت خودکار انجام می‌دهد:

  • چسباندن آدرس پایه بک‌اند (NEXT_PUBLIC_API_URL یا localhost:4000) به مسیر؛
  • خواندن توکن از localStorage و ارسال آن در هدر Authorization: Bearer … (فقط در مرورگر — روی سرور null برمی‌گردد)؛
  • ست Content-Type: application/json؛
  • در پاسخ غیر‌موفق، خواندن فیلد error از بدنه JSON و پرتاب آن به‌عنوان Error با پیام فارسی.
// خلاصه lib/api.ts
const API_URL = process.env.NEXT_PUBLIC_API_URL || 'http://localhost:4000';

export async function api<T>(path, options = {}) {
  const token = getToken();                       // از localStorage
  const res = await fetch(`${API_URL}${path}`, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...options.headers,
    },
  });
  if (!res.ok) {
    // پیام خطای فارسی از بک‌اند → Error
    throw new Error((await res.json()).error ?? 'درخواست ناموفق بود');
  }
  return res.json() as Promise<T>;
}

// میان‌برهای متد
export const apiGet    = (path)         => api(path);
export const apiPost   = (path, body)   => api(path, { method: 'POST',  body: JSON.stringify(body) });
export const apiPut    = (path, body)   => api(path, { method: 'PUT',   body: JSON.stringify(body) });
export const apiPatch  = (path, body)   => api(path, { method: 'PATCH', body: JSON.stringify(body) });
export const apiDelete = (path)         => api(path, { method: 'DELETE' });

۷ · احراز هویت

ورود مبتنی بر توکن، در دو قطعه: Context و Guard

۱) AuthContext — حافظه سراسری وضعیت ورود

src/context/AuthContext.tsx یک Provider است که در چیدمان ریشه دور کل برنامه قرار گرفته و این API را با هوک useAuth() ارائه می‌کند:

عضونوعتوضیح
userUser | nullکاربر جاری؛ null یعنی مهمان
loadingbooleanتا پایان بازیابی از localStorage در اولین mount
login(token, user)تابعنوشتن token و user در localStorage + آپدیت state
logout()تابعپاک کردن هر دو کلید و خالی کردن state

در اولین بارگذاری، user از localStorage خوانده و parse می‌شود (اگر خراب بود حذف می‌شود) و loading خاموش می‌شود. به این ترتیب با رفرش صفحه، نشست کاربر از بین نمی‌رود.

۲) AuthGuard — محافظت مسیر در سطح چیدمان

منطق کامپوننت AuthGuard که دور کل پنل‌ها قرار می‌گیرد:

شرطنتیجه
loading === trueانتظار؛ رندر «در حال بارگذاری...»
کاربر وارد نشدهrouter.replace('/login')
role="admin" ولی نقش کاربر userrouter.replace('/panel')
در غیر این صورترندر children (خودِ صفحه)

چون این منطق در layout.tsx هر پنل است، تمام صفحات زیرمجموعه به‌طور خودکار محافظت می‌شوند و لازم نیست هر صفحه جداگانه گارد داشته باشد. Navbar هم بر اساس همان Context خودش را تطبیق می‌دهد: مهمان → دکمه‌های ورود/ثبت‌نام؛ کاربر → «پنل کاربر»؛ ادمین → «پنل ادمین» + نام + خروج.

مرز امنیت: AuthGuard صرفاً یک محافظ «تجربه کاربری» در مرورگر است؛ نقش و توکن در localStorage قابل دستکاری‌اند. مرجع واقعی مجوزها همان بک‌اند است که هر درخواست اداری را با middleware و JWT اعتبارسنجی می‌کند (Express + jsonwebtoken). فرانت فقط UI را بر اساس نقش شکل می‌دهد.
۸ · الگوی داده

دریافت داده با useEffect، بازخوانی بعد از هر تغییر

هیچ کتابخانه‌ای مثل React Query استفاده نشده؛ هر صفحه الگوی ثابت و یکسانی را تکرار می‌کند:

  1. وضعیت محلی با useState: داده‌ها، loading، error (و در فرم‌ها: saving/msg).
  2. یک تابع load() که با apiGet داده می‌گیرد و state را پر می‌کند.
  3. فراخوانی load() در useEffect هنگام mount صفحه.
  4. بعد از هر عملیات نوشتن (ذخیره/حذف/تغییر وضعیت) دوباره load() — یعنی «بازخوانی کامل لیست» به‌جای به‌روزرسانی محلی کش.
  5. رندر سه‌حالته: پیام بارگذاری → خطا/حالت خالی → محتوا.

جستجوی زنده با debounce

در صفحه قطعات، تایپ در کادر جستجو state را عوض می‌کند و یک useEffect وابسته به آن با ۳۵۰ میلی‌ثانیه مکث درخواست را می‌فرستد — تا با هر حرف یک درخواست نرود: 

useEffect(() => {
  const timer = setTimeout(() => {
    loadParts(search);               // GET /api/parts?q=…
  }, 350);
  return () => clearTimeout(timer); // تایمر قبلی لغو می‌شود
}, [search]);

موازی‌سازی و اشتراک داده

  • داشبورد ادمین سه درخواست مستقل را با Promise.all هم‌زمان می‌گیرد و فقط «طول لیست‌ها» را به‌عنوان آمار نشان می‌دهد.
  • فرم قطعهٔ ادمین، لیست دسته‌بندی‌ها را همزمان با لیست قطعات می‌گیرد تا select دسته پر شود.
  • فرم افزودن/ویرایش یک فرم واحد است: کلیک «ویرایش» در جدول، فرم بالای صفحه را با دادهٔ آن ردیف پر می‌کند (editingId تعیین می‌کند دکمه، «افزودن» باشد یا «ذخیره تغییرات» و درخواست POST یا PUT برود).

لایه ۲ — CSS Modules: استایل اختصاصی هر صفحه

هر صفحه/کامپوننت فایل *.module.css خودش را دارد (مثل page.module.css، PanelLayout.module.css) و در ادمین یک shared.module.css مشترک برای جدول‌ها و فرم‌ها. این یعنی بدون Tailwind یا کتابخانه UI، هم scope ایزوله داریم و هم سازگاری کلاس‌ها تضمین شده.

فارسی‌سازی و RTL

  • <html lang="fa" dir="rtl"> در چیدمان ریشه — همه چیدمان‌ها راست‌چین می‌شوند.
  • فونت وزیرمتن با next/font/google (subsetهای arabic و latin، display: swap) به‌صورت متغیر CSS تزریق می‌شود.
  • اعداد و قیمت‌ها همه‌جا با toLocaleString('fa-IR') فارسی و جداکننده هزارگان می‌شوند.
  • فیلدهایی که محتوایشان لاتین است (ایمیل، رمز، کد فنی، قیمت) با dir="ltr" هنگام تایپ و نمایش درست رندر می‌شوند.

سه سناریوی کلیدی، گام‌به‌گام

ورود / ثبت‌نام

  1. کاربر فرم را submit می‌کند → POST /api/auth/login (یا register).
  2. پاسخ شامل token و user است → login(token, user) آن‌ها را در localStorage و Context می‌گذارد.
  3. هدایت بر اساس نقش: ادمین → /admin، کاربر → /panel (ثبت‌نام هم بلافاصله واردشده تمام می‌شود).

ثبت سفارش

  1. در /parts/:id دکمه «سفارش این قطعه» (غیرفعال اگر موجودی صفر است).
  2. اگر وارد نشده → هدایت به /login.
  3. POST /api/orders با items: [{ partId, quantity: 1 }] — سفارش تک‌قطعه‌ای، بدون سبد خرید.
  4. پیام موفقیت؛ سفارش در /panel/orders از GET /api/orders/mine دیده می‌شود.

مدیریت داده در پنل ادمین (الگوی CRUD)

  1. صفحه با load() باز می‌شود: لیست موجود + داده‌های کمکی (مثلاً دسته‌ها).
  2. «افزودن» → POST؛ «ویرایش» → پر شدن فرم و PUT /…/:id؛ «حذف» → تأیید با confirm() و DELETE.
  3. بعد از هر عملیات موفق، پیام فارسی نمایش و load() دوباره اجرا می‌شود تا جدول همیشه با سرور هم‌گام باشد.

نکات شفاف و مسیرهای بهبود

این‌ها باگ نیستند؛ نقاطی‌اند که در توسعه بعدی ارزش تصمیم‌گیری دارند:

  • محافظت مسیر فقط سمت کلاینت است. یک middleware.ts در ریشه Next می‌تواند قبل از ارسال JS هم مسیرهای /panel و /admin را بگیرد و فلش «در حال بارگذاری...» را حذف کند.
  • توکن در localStorage در برابر XSS آسیب‌پذیر است؛ گزینه امن‌تر cookie با httpOnly است (نیازمند تغییر در بک‌اند).
  • داشبورد برای سه عدد، سه لیست کامل را می‌گیرد؛ یک endpoint آماری (یا count) سبک‌تر است.
  • سبد خرید وجود ندارد — هر سفارش یک قطعه با quantity=1 است؛ ساختار items[] بک‌اند برای سبد آماده است.
  • خطای صفحه خانه بی‌صدا قورت داده می‌شود (catch → [])؛ کاربر نمی‌فهمد چرا لیست خالی است.
  • تصاویر با <img> خام رندر می‌شوند (خود کد هم eslint-disable دارد)؛ next/image بهینه‌سازی و lazy-load می‌دهد.
  • کدهای کمکی تکراری (formatPrice در ۵ فایل، statusLabel در ۲ فایل) — قابل انتقال به lib/.
  • ظرفیت استفاده‌نشده از Server Components: چون همه صفحات کلاینت‌اند، لیست قطعات عمومی می‌تواند داده را روی سرور بگیرد و HTML اولیه پرتحویل بدهد (بهتر برای سئو و سرعت اولیه).
جمع‌بندی: معماری، ساده و آگاهانه انتخاب‌شده است — لایه‌های تمیز (routes / context / lib / components)، یک دروازه API واحد، گارد مسیر در سطح layout و دیزاین‌سیستم توکن‌محور. همین سادگی باعث می‌شود هر یک از بهبودهای بالا بدون بازنویسی، به‌صورت افزایشی قابل افزودن باشد.
